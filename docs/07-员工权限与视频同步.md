# 07 · 员工分权限 · 视频同步 · 离线字段级合并

> 版本：IPA 1.4.0 (build 11) · 后台 `meiyan.shengka.net` · 数据库 schema v4
> 完成时间：2026-11-10

这一轮补的是上一版明确留下的三块硬骨头：**多人分权限**、**视频和照片一样能同步**、**离线改动只合并自己动过的字段**。

## 一、员工账号与分权限

### 1.1 为什么需要

上一版只有一个店主账号。实际店里是「老板 + 店长 + 几个美容师 + 前台」一起用，全都用店主账号有两个问题：谁改的都算店主改的，出事查不出来；美容师能看见充值卡生成、短信密钥、全库备份，权限过大。

### 1.2 权限模型：两层

权限拆成两层，避免「角色只有 5 种、总有一种不完全合适」的尴尬。

| 层 | 字段 | 含义 |
|---|---|---|
| 模块层 | `modules: []` | 能进哪几个业务菜单（客户/预约/收款/产品/…共 16 个） |
| 能力层 | `caps: {}` | 几项特殊动作：`write` 写入、`staff` 员工管理、`settings` 店铺设置、`sms` 短信、`backup` 备份、`recharge` 充值卡、`sync` 同步接口、`ipa` 安装包 |

数据库里 `admins` 表加了一列 `perms TEXT`，存 `{"modules":[...],"caps":{...}}`。空着就用角色预设，填了就按填的来 —— **预设是起点，不是牢笼**。

### 1.3 五种角色预设

| 角色 | key | 能进的模块 | 特殊能力 |
|---|---|---|---|
| 店主 | `owner` | 全部 16 个 | 全开 |
| 店长 | `manager` | 除「员工」「设置」外全部 | 除 `staff`/`settings` 外全开 |
| 美容师 | `therapist` | 客户、预约、步骤、笔记、领用、照片、对比、导师、产品 | 只有 `write` |
| 前台 | `frontdesk` | 客户、预约、收款、套餐、会员、开通、钱包 | 只有 `write` |
| 只读 | `viewer` | 全部 | 无（不能写） |

旧数据里的 `staff` / `admin` / `member` 在迁移时被归一化成 `manager` / `owner` / `viewer`，老账号不会失效。

### 1.4 服务端拦截点

不是前端藏按钮就算完，每个入口都在服务端再判一次：

```php
// 列表 / 详情：读权限
case 'list':
    $me = admin_required();
    perm_check_module($me, $key, false);

// 新增 / 编辑 / 删除：写权限
case 'save':
    perm_check_module($me, $key, true);

// 敏感动作：能力位
case 'admin/backup-create':
    perm_check_cap(admin_required(), 'backup');
```

一共 25 个敏感路由加了 `perm_check_cap`：备份 5 个、安装包 2 个、充值卡 9 个、同步 4 个、设置保存 1 个、短信 4 个、上传 1 个。模块级拦截覆盖 `list` / `save` / `delete` 三个通用路由。

### 1.5 后台界面

左侧「系统」组新增**员工管理**（`staff`）。列表显示头像首字、姓名、邮箱、角色标签、状态、最近登录。编辑弹窗里：

- 上半部分五个角色卡片单选，选中即预览该角色的默认权限
- 下半部分两个勾选网格：模块权限（16 个）+ 特殊能力（8 个）
- 改过勾选后角色卡片变成「自定义」，保存的是 `perms` 而不是角色名

三条硬保护：**不能把自己降级**、**不能删自己**、**至少保留一个店主账号**。

## 二、视频同步

### 2.1 数据模型

`photos` 表从「一张图」扩成「一个媒体」：

| 新列 | 类型 | 说明 |
|---|---|---|
| `kind` | `VARCHAR(10)` | `image` / `video` |
| `duration` | `DOUBLE` | 视频时长（秒），照片 0 |
| `thumb_name` | `VARCHAR(120)` | 封面文件名 |
| `thumb_url` | `VARCHAR(255)` | 封面云端地址 |
| `size_bytes` | `BIGINT` | 原始体积 |

App 端 `PhotoItem` 同步加了 `kind` / `duration` / `thumbName`，`init(from:)` 用 `decodeIfPresent` 兜底，老版本本地数据读进来默认 `image`，不会崩。

### 2.2 导入：抽帧做封面

视频不能直接当缩略图，导入时用 AVFoundation 抽一帧存 jpg：

```swift
let asset = AVURLAsset(url: dst)
let seconds = CMTimeGetSeconds(asset.duration)
let gen = AVAssetImageGenerator(asset: asset)
gen.appliesPreferredTrackTransform = true          // 竖屏视频不会转倒
gen.maximumSize = CGSize(width: 900, height: 900)  // 封面不存原尺寸
let at = CMTime(seconds: min(1.0, max(0, duration / 3)), preferredTimescale: 600)
if let cg = try? gen.copyCGImage(at: at, actualTime: nil) { ... }
```

抽第 1 秒，视频不足 3 秒就抽 1/3 处 —— 太靠头常常是黑帧。

从系统相册取视频用 `Transferable` + `FileRepresentation`，先复制到临时目录再处理，**不把整段视频读进内存**。

### 2.3 上传：三条容易踩的坑

**坑一：MIME 写死。** 原来 `uploadImage` 里 `Content-Type` 固定 `image/jpeg`，服务端 `finfo` 一看内容不是图片就拒。改成按扩展名给：

```swift
case "mp4", "m4v": mime = "video/mp4"
case "mov", "qt":  mime = "video/quicktime"
```

**坑二：超时。** 原 60 秒，200MB 视频必然断。视频给 900 秒请求超时 / 1800 秒资源超时。

**坑三：内存。** 200MB 视频 + multipart 拼接 = 内存里同时躺 400MB，老机型直接被杀。超过 24MB 就落临时文件走流式上传：

```swift
if body.count > 24 * 1024 * 1024 {
    let t = FileManager.default.temporaryDirectory.appendingPathComponent("up-\(UUID()).part")
    try body.write(to: t)
    body = Data()                      // 及时释放
    (respData, _) = try await session.upload(for: req, fromFile: t)
} else {
    req.httpBody = body
    (respData, _) = try await session.data(for: req)
}
```

### 2.4 服务端校验

`upload` 路由从「只认图片」改成两条通道：

```php
$info = @getimagesize($f['tmp_name']);
if ($info) {
    // 图片：getimagesize 验真，扩展名以真实类型为准，上限 12MB
} else {
    // 视频：扩展名白名单 + finfo MIME 双重校验，上限 200MB
    $allowed = ['mp4', 'mov', 'm4v', 'qt'];
    if ($mime !== '' && strpos($mime, 'video/') !== 0 && $mime !== 'application/octet-stream')
        fail('文件内容不像视频（' . $mime . '）');
}
```

只看扩展名会被改名的文件骗过去，所以内容也验。nginx `client_max_body_size` 和 `.user.ini` 的 `upload_max_filesize` 都已放到 200M。

实测四种情况：

| 上传 | 结果 |
|---|---|
| 2×2 PNG | 200 `kind=image` |
| 最小 mp4（ftyp box） | 200 `kind=video` |
| 同上改名 .mov | 200 `kind=video` |
| 文本文件改名 .mp4 | 400 文件内容不像视频（text/plain） |

### 2.5 同步链路

视频本体和封面是**两条独立的上传通道**，因为后台只需要封面就能显示列表，没必要为了一张缩略图等 100MB 传完：

```
视频 mp4  ──upload──►  /uploads/202611/xxx.mp4   → row.url
封面 jpg  ──upload──►  /uploads/202611/xxx.png   → row.thumb_url
```

`sync_modules()` 的 `photos` 定义补齐五个字段，类型转换表加 `size_bytes` 为 int、`duration` 为 float。推送、拉取、合并三处都过这一张表，所以加字段只改一处。

实测一条视频记录 push → 落库 → pull 回读：

```
kind       = 'video'
duration   = 12.5
thumb_name = 'abc-thumb.jpg'
thumb_url  = '/uploads/202611/10182719-cddd0b90.png'
size_bytes = 1048576
file_name  = 'abc.mp4'
caption    = '视频同步测试'
```

### 2.6 界面

相册页顶部提示条多一个「加视频」按钮（`PhotosPicker(matching: .videos)`）。视频格子在列表里显示封面 + 中间播放图标 + 右下角时长角标（`0:12`）。点开全屏 `VideoPlayer`，黑底、顶部标题 + 关闭。本地文件不在时显示「等同步完成后会自动下载」，而不是一个空白播放器。

## 三、离线编辑的字段级合并

### 3.1 问题

上一版是整行 LWW：谁的时间戳新，整行覆盖。两个人同时改同一个客户时，A 改电话、B 改备注，后提交的那个会把另一个人的改动抹掉 —— 因为整行都算「它的」。

### 3.2 做法：每列一个时间戳

12 张业务表都加了 `field_ts TEXT`，存 `{"phone":"2026-11-10T18:18:36+08:00","note":"..."}`。

**App 端**维护一份「上次同步后的快照」，每次推送前跟快照比，只有值变了的字段才打当前时间：

```swift
for (k, v) in row where !skip.contains(k) {
    if Self.canonical(old[k]) != Self.canonical(v) {
        out[k] = nowIso          // 只有动过的字段带时间戳
    }
}
```

第一次同步某条记录时全部字段都打时间戳（服务端没有基线，全量插入）。

**服务端**看到 `field_ts` 就进入逐列比对模式：

```php
foreach ($row as $col => $v) {
    if (!array_key_exists($col, $ftsIn)) continue;   // 客户端没动这列，保持服务端值
    $cTs = strtotime($ftsIn[$col]);
    $sTs = isset($serverFts[$col]) ? strtotime($serverFts[$col]) : $existTs;
    if ($cTs >= $sTs) { 覆盖，并更新该列时间戳 }
    else              { $rejected[$col] = $exist[$col]; }   // 服务端更新，回传服务端值
}
```

返回里带 `merged`，App 拿到后把被拒的字段改回服务端的值 —— 用户看到的是「我改的没生效，因为别人更新」，而不是「我改的莫名其妙没了」。

### 3.3 后台保存也要打时间戳

这是最容易漏的一环：如果后台改电话不更新 `field_ts`，App 用一个旧时间戳就能把后台的改动覆盖掉。所以 `save` 路由里给所有改动的列盖当前时间：

```php
$stampFts = function (array $cols, ?array $base) use ($hasFts): ?string {
    if (!$hasFts) return null;
    $ft = $base ?: []; $t = date('c');
    foreach ($cols as $c) {
        if (in_array($c, ['uid','updated_at','field_ts','created_at'])) continue;
        $ft[$c] = $t;
    }
    return json_encode($ft, JSON_UNESCAPED_UNICODE);
};
```

### 3.4 三场景实测

同一个客户，后台和 App 各改不同字段：

| 步骤 | 操作 | 结果 |
|---|---|---|
| 1 | 后台把电话改成 `13999999999` | `field_ts.phone = 2026-11-10T18:18:36+08:00` |
| 2 | App 只改备注，`field_ts` 只带 `note` | 保存成功，**电话保住** |
| 3 | App 用 5 分钟前的时间戳想改电话 | `saved:0, skipped:1, merged:[{uid, fields:{phone:"13999999999"}}]` |
| 4 | 最终状态 | `phone=13999999999`（后台的）、`note=离线改的备注`（App 的） |

两边都没丢，这正是要的结果。

### 3.5 兼容老版本

没带 `field_ts` 的请求走原来的整行 LWW，行为完全不变。所以 1.3.0 的包连上来不会出错，只是享受不到字段级合并。

## 四、数据库迁移

`SCHEMA_VERSION` 从 3 升到 4，`db()` 启动时比对 `settings.schema_version`，落后就跑 `migrate_schema()`。MySQL 5.7 没有 `ADD COLUMN IF NOT EXISTS`，所以用 `information_schema` 先判存在：

```php
$fresh = !table_exists($pdo, 'settings');
if ($fresh) { init_schema($pdo); seed_data($pdo); schema_set_version($pdo, SCHEMA_VERSION); return $pdo; }
if (schema_version($pdo) < SCHEMA_VERSION) {
    init_schema($pdo); migrate_schema($pdo); seed_recharge($pdo); schema_set_version($pdo, SCHEMA_VERSION);
}
```

v4 迁移内容：`admins.perms` / `admins.note`、12 张表 `field_ts`、`photos` 五个视频列。线上实测：`schema_version=4`，`photos` 列清单含 `kind,duration,thumb_name,size_bytes,thumb_url`，一次性完成，无手工 SQL。

## 七、还没做的

- **多店铺**：现在是单店铺。真要多店，`settings` 表要按 `shop_id` 分区，所有业务表加 `shop_id`，登录时确定店铺上下文。工作量大，等确认要不要。
- **后台播放视频**：后台照片列表目前显示封面和「视频」标记，点击跳到新窗口用浏览器原生播放器打开 mp4。嵌 `video` 标签做内嵌播放是小事，但需要先确认后台要不要支持。
- **视频转码**：现在原样存 mp4/mov，iPhone 录的 HEVC 在某些 Windows 浏览器里放不出来。要通用就得服务端转 H.264，需要 ffmpeg 和额外 CPU。
