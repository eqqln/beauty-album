# 09 · 多板块（多租户）与网址加密

> 版本：IPA 1.6.0 (build 15) · 后台已上线 `meiyan.shengka.net`
> 完成时间：2026-11-12

## 这一轮解决什么

1.5.1 之前，**所有激活的机器共用一套数据**。A 店激活了，B 店也激活了，两家的客户、相册、护理步骤、产品、预约全堆在同一个库里，列表互相看得见。这一轮把"一个激活码 = 一个独立板块"做实：

- 激活时**必须填使用人姓名 + 手机号**，服务端凭这两个字段开一块独立板块
- 这块板块里的客户 / 相册 / 步骤 / 产品 / 预约 / 会员 / 充值卡，**别人一块都看不到**
- 后台多了「板块管理」页，能看到每块板归属谁、多少台设备、多少条资料
- 换手机用同一张码重新激活，可以在后台点「恢复到手机」，把云端资料整份接回来
- App「我的」页里的服务器网址**默认加密显示**，后台可切回明文；内置地址在二进制里也是密文

## 板块级一键备份

后台「板块管理」每张卡片上都有 **⬇ 备份下载**，点一下就把这一块板（这一个人）的全部资料打成一个 zip 下到本地：

```
板块备份-刘宁-t16-20261112-015352.zip
├── 备份说明.txt              人看的说明（归属人、条数、文件数）
├── manifest.json             文件清单（每个文件的大小）
├── data.json                 完整数据：所有表所有字段，技术人员用它还原
├── data/                     同一批数据的中文表头 CSV，Excel / WPS 直接打开
│   ├── 01-客户（customers）.csv
│   ├── 02-相册与视频（photos）.csv
│   ├── 03-前后对比图（compares）.csv
│   ├── 04-预约记录（appointments）.csv
│   ├── 05-护理步骤（client_steps）.csv
│   ├── …共 17 张表
│   └── 17-导师（mentors）.csv
└── media/                    这块板的全部图片与视频
    └── t16/202611/xxx.jpg    路径与数据库里的 /uploads/t16/... 一一对应
```

几个关键设计：

- **只导出这一块板**。17 张业务表全部 `WHERE tenant_id=?`；授权码、设备、流水按板块筛；媒体只取 `uploads/t{id}/`（默认板块取 uploads 根下但跳过 `t{数字}` 目录）。不会串到别人的板里
- **空表也写表头**。没有数据的表（比如刚开的板还没有收款）会输出一行中文表头，而不是 0 字节空文件 —— 否则店主打开是一片空白，会以为导出坏了
- **列名换中文**。`tenant_export_labels()` 是一张列名对照表，没覆盖到的列保留原名，保证不漏字段
- **图片按两路取**：先整目录走 `uploads/t{id}/`，再按数据库里登记的地址（photos.url / thumb_url、compares、products.cover/images、mentors.photo、二维码设置项）兜一遍，两路取并集
- **只留最近 10 份**，防止把磁盘堆满；删板块时连它的备份包一起删

接口：

| 路由 | 说明 |
|---|---|
| `admin/tenant-export` | 生成备份包，返回 `file / rows / media / size_text` |
| `admin/tenant-export-download` | 按 `id + file` 流式下载，文件名做 `basename` 处理，只允许本板块目录下的 `.zip` |
| `admin/tenant-export-list` | 这块板已有的备份包 |

实测：一块板里放 1 客户 / 1 相册 / 1 步骤 / 1 笔记 / 1 预约 / 1 收款 / 1 产品 + 1 张图，导出 11 条数据、1 个文件、9.1 KB，包内 21 个条目（17 CSV + data.json + manifest + 说明 + 图片）。默认板块（含视频）导出 25 条数据、6 个媒体文件、297.6 KB。`data.json` 里客户表只有本板块那 1 条，默认板块的 2 条没混进来。

## 数据模型（schema 7）

`db.php` 的 `SCHEMA_VERSION` 由 5 升到 7：

- **6**：新增 `tenants` / `tenant_settings`，19 张业务表加 `tenant_id`
- **7**：修默认板块 id（见下面"踩坑 1"）

| 表 | 作用 | 关键列 |
|---|---|---|
| `tenants` | 板块本体，一行 = 一个客户 | `id`（0 = 默认板块）、`name`、`phone`、`shop_name`、`code`、`status`、`restore_flag`、`restore_at`、`restored_at`、`device_count` |
| `tenant_settings` | 板块级设置覆盖 | 主键 `(tenant_id, k)`，`v` |

加 `tenant_id` 的表（19 张）：`members`、`mentors`、`products`、`agents`、`agent_orders`、`customers`、`photos`、`compares`、`payments`、`appointments`、`client_steps`、`client_notes`、`product_claims`、`packages`、`member_packages`、`wallet_logs`、`recharge_cards`、`backups`、`admins`；另有 `activation_codes`（可空，NULL = 还没绑板块）与 `activations`。

**`tenant_id = 0` 是默认板块**，承接改造前的全部老数据。默认板块不删、不改归属。

### 唯一键必须跟着改

`members.phone` 原来是全局 `UNIQUE`。两个板块各有一个 `13800138000` 的会员时，第二条直接插不进去。`tenant_relax_unique()` 把单列唯一换成 `uk_tenant_phone(tenant_id, phone)`；换不动就降级成普通索引，至少不挡写入。

## 板块是怎么认出来的

`tenant_current_id()` 按优先级取，取到就 static 缓存，一个请求只算一次：

1. **设备凭证**：`Authorization: Bearer <token>` → `device_tokens` → `activations.tenant_id`（App 端最常用）
2. **管理员自身**：`admins.tenant_id > 0` 时锁死在自己那块板，不能切
3. **请求头** `X-Tenant-Id`：平台账号（`admins.tenant_id = 0`）在后台顶栏切板块时带
4. 都没有 → `0`（默认板块）

配套函数：`tenant_where()` 拼条件、`tenant_append()` 补参数、`tenant_setting_get/set()` 读写板块设置。

### 哪些设置是板块级，哪些是全局

`tenant_setting_keys()` 是白名单，命中才走 `tenant_settings`：

```
shop_name / shop_slogan / before_label / after_label / step_template / app_features
contact_phone / contact_wechat / notice / recharge_*
```

`license_*`（授权闸门开关）、`sms_*`（短信通道）、`ipa_*`（安装包）、`schema_version` 留在全局 `settings` —— 这些是平台级配置，不能按板块各配一份。

## 激活即开板块

`license/redeem` 新增入参 `name` / `phone`。逻辑在事务里：

```
激活码已绑板块（tenant_id 非空）？
  ├─ 是 → 板块存在？状态正常？手机号对得上？
  │        对不上就报「这张激活码已归属「XXX」，请使用你自己的激活码」
  └─ 否 → 姓名必填、手机号格式校验
           → tenant_ensure(name, phone, code)
           → UPDATE activation_codes SET tenant_id=...
           → 记一条「开板块」流水
```

`tenant_ensure()` **先按手机号找人**：找到就复用原板块（换码续费、换手机重装都不会丢数据），找不到才新建，并 `tenant_copy_defaults()` 从默认板块继承 `shop_slogan / before_label / after_label / step_template / app_features`，`shop_name` 用使用者姓名，同时复制一份默认板块的 `packages`。

`redeem` / `verify` 的返回都加了 `tenant_id / tenant / owner_name / owner_phone / restore`。板块被停用时 `verify` 直接 403。

## 数据隔离落在哪

- **通用 CRUD**（`list` / `save` / `delete` / `options`）：`list` 自动拼 `tenant_id = ?`；`save` 更新时带 `AND tenant_id=?`（防止 A 板块改到 B 板块的行），新增时写当前板块；`delete` 同理
- **同步**（`sync_pull` / `sync_push` / `sync_delete` / `sync_stats`）：拉取带板块条件；推送查重是 `WHERE uid=? AND tenant_id=?`，UPDATE 也带板块
- **统计**（`stats/overview`）：全部按板块重算，返回 `tenant_id` + `tenant`
- **会员**（`register` / `login` / `reset` / `activate`）：按板块隔离；充值卡跨板块使用时拦下「这张卡不属于当前门店」
- **上传**：目录改成 `uploads/t{tenant_id}/{Ym}/`，不同板块的文件不混在一个目录
- **钱包流水**：`wallet_log()` 从 `members` 反查 `tenant_id` 落库 —— 跟会员走，不跟请求走

## 换机恢复

### 靠什么认出「还是这个人」

三层钥匙，从硬到软：

| 层 | 依据 | 什么时候生效 |
|---|---|---|
| 1 | 设备凭证 `device_tokens → activations.tenant_id` | 同一台手机，不用重填 |
| 2 | 激活码 `activation_codes.tenant_id` | 新手机 + 同一张码，**跟名字无关** |
| 3 | 手机号 `tenant_ensure()` 按 phone 查 | 新手机 + 同一手机号 |

所以**认人的钥匙是手机号，认板块的钥匙是激活码**。名字只在「第一次开板」时写进去，之后改名不影响归属。

不需要再单独造一个「恢复码」：**激活码本身就是那个专属码**。它第一次被兑换时就钉死在一块板上（`activation_codes.tenant_id`），之后不管谁拿着、在哪台手机上输，都进同一块板、同一批资料。

### 换手机的四步

```
① 后台「激活码 → 设备」→ 旧手机点「解绑」   ← 名额收回来，旧机下次打开要重新激活
② 新手机装 App → 输同一张激活码（姓名电话自动带出，或重填同一手机号）
③ 后台「板块管理」→ 找到这个人 → 点「恢复到手机」
④ 新手机打开 App → 弹「从服务器恢复资料」→ 确认 → 整份拉回
```

第 ① 步不能省：`max_devices` 默认是 1，不解绑新手机激活会直接被拒，提示「这张激活码的 1 台设备名额已用完。换手机请先在后台『激活码 → 设备』里把旧手机解绑」。解绑只收回名额、作废旧机凭证，**板块里的数据一条不动**。

### 恢复时的执行顺序

```
后台点「恢复到手机」 → tenants.restore_flag = 1
        ↓
App 下次激活 / 回前台复核 → verify 返回 restore: true
        ↓
RootView 弹「从服务器恢复资料」 → SyncService.restoreFromServer()
        ↓
syncPull(since: nil) 全量拉 → 云端有数据才清本地 → merge → 下载图片
        ↓
license/restore-ack → 清 restore_flag
```

**顺序不能反**：先拉、确认有数据、再清本地。拉取失败时本地数据还在，不会出现「清空后发现云端是空的」。

云端是空的（`counts` 全 0）时**不清本地**，只合并 —— 防止把手机上的资料删掉。

## 网址加密

同一个算法两端各写一遍，必须完全一致：**逐字节 XOR 固定密钥 `MYA2026K`，再标准 Base64，去掉尾部 `=`**。

- PHP：`util.php` 的 `url_encode()` / `url_decode()`
- Swift：`ServerURL.encode()` / `decode()`

`https://meiyan.shengka.net` → `JS01QkMIGWQgPChLUVwYOCU8L1VbUxglKC0`

三处用途：

1. **内置地址不落明文**：Swift 里以密文常量 `builtinCipher` 存，运行时 `decode` 出真地址。`strings BeautyAlbum` 搜不到域名
2. **界面显示可切**：后台「系统设置 → 网址显示方式」选加密/明文，`site/info` 下发 `url_display`，App 存 `UserDefaults("site.url.display")`，`ServerURL.display()` 按开关渲染。「我的」页用等宽字体 + 中间截断
3. **接口同时给两种**：`site/info` 返回 `api_base`（按开关给明文或密文）和 `api_base_enc`（永远密文）

> 注意：这是**混淆**不是加密。目的是让别人截图 / 抓包时抄不走域名，挡不住真的逆向。密钥是硬编码的，改域名时要两端同步改密文。

## 踩坑

**1. 默认板块 id 被自增改成 1**

`INSERT INTO tenants(id, ...) VALUES(0, ...)` 在默认 `sql_mode` 下会被当成"请给我一个自增号"，结果落成 `id=1`。而所有老数据的 `tenant_id` 都是 `0`，两边对不上 —— 后台板块列表里默认板块显示 0 条资料，真实数据（客户 2 / 照片 2 / 步骤 12 / 预约 3）全成了孤儿。

修法：迁移时先 `SET SESSION sql_mode=CONCAT(@@sql_mode,',NO_AUTO_VALUE_ON_ZERO')` 再插；同时加一段修复逻辑，把之前误插成 `id>0` 的那条默认板块搬回 `0`。为此把 `SCHEMA_VERSION` 从 6 提到 7，让线上库重跑一次迁移。

**2. 删板块被"已停用"的设备挡住**

原来的守卫是 `COUNT(*) FROM activations WHERE tenant_id=?`，把 `已停用 / 已解绑 / 已过期` 的记录也算成占用，导致"设备都解绑了还是删不掉"。改成只数 `status='生效中'`，并在删除时连带清掉 `device_tokens` 与 `activations`，不留悬空行。

**3. 单行字符串里写裸换行**

```swift
Text("第一行
第二行")
```

Swift 单行字符串字面量不允许裸换行，直接编译失败。改成 `\n`。

**4. `license/redeem` 路由漏传 name/phone**

`lib/license.php` 的 `license_redeem()` 已经改成读 `$in['name']` / `$in['phone']`，但 `index.php` 的路由没把这两个字段塞进去，导致**永远报"请填写使用人姓名"**，激活直接走不通。补上。

**5. 混淆白做了 —— 兜底字符串把域名写回二进制**

```swift
static var builtin: String {
    let v = decode(builtinCipher)
    return v.isEmpty ? "https://meiyan.shengka.net" : v   // ← 就是这一行
}
```

看着像是"解不出来就用默认值"的安全写法，实际把明文域名原样编进了二进制。出包后 `strings` 一搜就命中，前面的密文常量等于白存。删掉兜底，`decode` 解不出来就返回空串。

**6. 激活即要求恢复时，弹窗不出现**

`redeem()` 里 `restoreNeeded = ...` 写在 `state = .active` **之前**，而 RootView 靠 `onChange(of: license.restoreNeeded)` 弹窗，判断条件是 `license.state == .active` —— 那一刻 state 还是 `.inactive`，于是永远不弹。修法：在 `onChange(of: license.state)` 里也补查一次 `restoreNeeded`。

**7. `version_compare("1.6.0(15)", "1.6.0")` 返回 -1 —— 新客户端被当成老版本**

App 上报的版本号是 `CFBundleShortVersionString(CFBundleVersion)`，也就是 `1.6.0(15)`。PHP 的 `version_compare` 遇到括号会当成"更低的分段"，于是 `1.6.0(15) < 1.6.0` 成立，代码判定为老客户端，**忽略用户填的姓名电话**，直接开了块「待补信息 XXXX」的空板。用户明明填了名字，后台看到的却是一个叫"待补信息"的板块，名字电话全没落上。

修法：先抽出数字部分再比 ——

```php
$verNum = preg_match('/^\s*(\d+(?:\.\d+)*)/', $appVersion, $m) ? $m[1] : '';
$legacy = $userName === '' && $userPhone === ''
          && $verNum !== '' && version_compare($verNum, '1.6.0', '<');
```

同时把判据改成"两个字段都空 + 明确是旧版本"才算兼容，只要客户端带了姓名或电话就走严格分支。这样即使版本号格式再变，也不会误判。

**8. `UI.confirmBox` 在 ui.js 里根本没导出**

`ui.js` 只导出了 `confirm: confirmBox`，但 `app.js` 里有三处写的是 `UI.confirmBox(...)`。`UI.confirmBox` 是 `undefined`，调用直接抛 TypeError，于是「恢复到手机」「删除板块」「备份下载」三个按钮点了**毫无反应**，控制台报错但页面不提示。

修法：三处改成 `UI.confirm`，并在导出里补 `confirmBox: confirmBox` 别名兜底。顺手把 `confirmBox` 的确定按钮文案从固定的"确定删除"改成按场景传（备份用"开始备份"、恢复用"确定"、删除才用"确定删除"），并给弹窗文案加 `white-space:pre-line` 让 `\n` 真的换行。

**9. 换手机根本激活不了 —— 设备名额没人收得回来**

`max_devices` 默认 1，第一次激活 `used_count` 就变 1。之后换手机，`used_count >= max` 直接抛「名额已用完」。而原来的「停用设备」只把 `activations.status` 改成已停用，**不碰 `used_count`**，所以名额永远收不回来，一张码只能用一台手机、坏了就废。

修法：新增 `admin/license-device-unbind`，一次做三件事 —— `status='已解绑'`、`used_count=GREATEST(used_count-1,0)`、删掉这台设备的 `device_tokens`。设备明细弹窗里加「解绑」按钮，并把报错文案改成"换手机请先在后台解绑"，让人知道下一步点哪。

## 当前边界

- 板块之间不能搬数据（比如 A 的客户转到 B）
- 一个手机号只能对应一块板块；一个人要开两家店得用两个号
- 平台账号（`admins.tenant_id = 0`）能在所有板块间切换，等于超级权限，只给老板用
- 恢复是**整份覆盖**，不做增量对比；本机独有的、从未上传过的资料会丢（弹窗里已写明）
- 网址混淆挡不住逆向，只能防截图抄域名
